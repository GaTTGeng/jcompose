# Docker Compose field support matrix

This matrix tracks **jcompose's** behavior against Docker Compose. ComposeSharp 3.0.0 is the sibling implementation used to synchronize feature scope; it does not define compatibility behavior. A matching Java API type does not mean the field is parsed or applied.

## Status definitions

| Status | Meaning |
| --- | --- |
| Implemented | Parsed and applied by jcompose, with behavior checked against Docker Compose. |
| Partial | A documented subset is parsed or applied; listed gaps remain. |
| Parsed only | Retained in the Java model, with no corresponding runtime behavior yet. |
| Planned | In the ComposeSharp 3.0.0 feature scope, but not implemented or verified in jcompose. |
| Unsupported | Known unsupported behavior; no compatibility claim is made. |

The repository is currently an early `3.0.0-SNAPSHOT`. When no Compose filename is explicitly supplied, jcompose prefers `compose.yaml` and searches conventional filenames from the working directory upward. Project loading also merges the matching optional conventional override file. Most Compose-shaped service fields are retained in `ServiceDefinition` as raw values. The engine implements a limited subset of build and service lifecycle behavior. Therefore, **no field should be read as full Docker Compose support unless its row explicitly says Implemented**. At this snapshot, no Compose service field has been verified as fully implemented against Docker Compose.

## Project and service fields

| Docker Compose field or behavior | jcompose model/API | Current status | Notes and target behavior |
| --- | --- | --- | --- |
| `services` and service names | `ComposeProject.services`, `ServiceDefinition` | Partial | The loader requires a non-empty service mapping, validates names against ASCII letters, digits, `_`, `-`, and `.`, and retains each service mapping. Multi-file overlays remove exact duplicates from Compose's unique service sequences; see [merge semantics](merge-semantics.md). Profile-gated services without `image` or `build` load when inactive; `up`, `create`, `run`, and `scale` reject a selected service without either field, matching Docker Compose's load-versus-runtime validation boundary. |
| `image`, `build`, `container_name`, `command`, `entrypoint` | `ServiceDefinition` raw fields | Partial | The loader requires `image` to be a YAML scalar and reports its Compose path on invalid mapping/list shapes. `build` invokes Docker Engine for local contexts and supports remote HTTP(S), Git, and SSH contexts passed to the daemon; remote Dockerfile resolution and remote credentials are handled by the daemon and are not independently verified. `dockerfile_inline` is accepted for local contexts, staged into the build archive, and rejected when combined with `dockerfile`; inline Dockerfiles with remote contexts are unsupported. Local Dockerfiles outside the context are staged into the archive; `.dockerignore` is applied by the context archiver, including Go-style character classes, escaped members, and Unicode scalar matching. Unix FIFOs are preserved, sockets are omitted, and device nodes are rejected. Full Docker CLI ignore matching is not verified. Basic container creation/reconciliation applies a subset of service settings. |
| `environment`, `env_file` | `ServiceDefinition` raw fields | Partial | Interpolation and basic env-file loading exist; malformed or unclosed braced expressions in YAML values fail with Compose property and source location. Simple environment maps/lists are applied at container creation. Key-only `environment` entries and bare keys in normal `env_file` format pass through matching host values and are omitted when unresolved. `env_file.required: false` skips a missing optional file, and `format: raw` preserves values without dotenv parsing. All Compose precedence/quoting rules are not implemented. See [loader compatibility](loader-compatibility.md). |
| `ports`, `expose` | `ServiceDefinition` raw fields | Partial | Short and long syntax expand target ranges into individual Docker bindings; equal-length published/target ranges pair port by port, while a published range for one target remains a range. Published port `0` is retained for dynamic host-port allocation. `expose` ranges expand too. The loader validates port list shape, short-syntax ports/ranges, and long-syntax `target`, `published`, `host_ip`, `protocol`, `mode`, `name`, and `app_protocol` values, and rejects unknown long-syntax options. Multi-file port merges use Docker Compose's `{ip, target, published, protocol}` key across short/long syntax. All protocol/address combinations, option interactions, and Compose formatting still need conformance coverage. See the official [Docker Compose service port reference](https://docs.docker.com/reference/compose-file/services/#ports). |
| `volumes` | `ServiceDefinition` raw fields | Partial | Basic short/long bind and named mounts are applied. Target-only short syntax creates Docker-managed anonymous volume mounts for services and one-off `run` containers. Short syntax preserves the drive-letter colon in Windows sources such as `C:\\data:/data:ro`, and `ro`/`readonly` mount flags are recognized. Bind mounts map the Compose `bind.propagation` values and SELinux `bind.selinux` options (`z`/`Z`) to Docker Engine. Short syntax and long syntax with `bind.create_host_path` omitted or true create a missing local source directory; long syntax with `bind.create_host_path: false` rejects a missing source. Explicitly configured anonymous volumes and image-declared volumes are reused by target across recreation unless `up.renewAnonVolumes` is enabled. Other Windows path edge cases and external-volume semantics are not verified. |
| `depends_on`, `profiles` | `ServiceDefinition`, `ComposeProjectContext` | Partial | Required undefined dependencies and malformed short/long dependency forms are rejected during loading; undefined `required: false` dependencies are skipped with a warning. Long form validates supported conditions and boolean `restart`/`required` values. `profiles` must be an array of strings whose names match `[a-zA-Z0-9][a-zA-Z0-9_.-]+`. Explicitly selecting a profiled service activates its profiles. Create/up/start order selected dependencies and reject required dependencies whose profiles are inactive; optional `required: false` dependencies with inactive profiles are skipped. Missing optional dependency containers, failed readiness states, and dependency wait timeouts warn and allow the dependent service to continue. `volumes_from` service dependencies are also rejected when their profiles are inactive. `pull --include-deps` follows `depends_on` profile rules. Other dependency edge cases remain incomplete. |
| `healthcheck`, `restart`, `deploy.replicas`, `deploy.restart_policy` | `ServiceDefinition` raw fields | Partial | Healthcheck test/timing values including `start_interval`, service restart policy, and replica counts are mapped. The loader validates healthcheck durations (including fractional and compound units such as `1.5s` and `1m30s`), service restart policy names and optional non-negative `on-failure` retry counts, retries, deployment replicas, and selected nested deployment values with service/property diagnostics. `deploy.restart_policy` takes precedence over `restart` and maps `none`, `any`, and `on-failure` plus `max_attempts` to Docker Engine; `delay` and `window` are not represented by the container restart policy. Other duration normalization and deployment semantics remain incomplete. |
| `networks`, `volumes`, `secrets`, `configs` at project scope | `ComposeProject` resource names and definitions | Partial | Named volume, network, secret, and config service references must match a declared project resource; bind mounts and the implicit `default` network are exempt. Network, volume, secret, and config definitions are retained and rendered. Project resources apply custom names, external-resource lookup, network driver/options, attachable/internal/IPv6 flags, subnet/IP-range/gateway IPAM entries, and volume drivers/options. File-backed secrets/configs granted to services are mounted read-only for service containers and one-off `run`; default targets are `/run/secrets/<name>` for secrets and `/<name>` for configs, and explicit targets are supported. The Docker daemon must be able to read the resolved host path, and host file permissions are unchanged. External, environment-backed, and inline-content secrets/configs are unsupported; file-source `uid`/`gid`/`mode` values are retained but not applied by this bind-mount backend. Windows secrets require an explicit target. External networks/volumes must already exist; IPAM options and several resource fields remain unapplied. |
| `labels`, `label_file`, `logging`, `hostname`, `domainname`, `user`, `working_dir` | `ServiceDefinition` raw fields | Partial | Service labels are applied. `label_file` paths resolve from the Compose project directory; listed files merge in order and inline labels take precedence. Container, project-resource, and image-build creation reject labels in Docker Compose's reserved `com.docker.compose` namespace; configuration loading/rendering retains them. Logging driver/options are passed to Docker Engine for service and one-off `run` containers; driver names must be present in docker-java 3.7.1's enum, so custom plugin driver names outside that list fail clearly. The remaining Docker Compose semantics are incomplete. |
| `privileged`, `read_only`, `tmpfs`, `cap_add`, `cap_drop`, `security_opt`, `devices`, `device_cgroup_rules`, `blkio_config`, `sysctls`, `ulimits`, `pids_limit`, `runtime`, `userns_mode`, `storage_opt` | `ServiceDefinition` raw fields | Partial | These values are mapped into Docker `HostConfig` for service and one-off `run` containers. `tmpfs` supports both the service-level path/options form and long-syntax `volumes` mounts with optional byte size and octal mode. `blkio_config` supports weight, per-device weights, read/write bytes-per-second, and read/write IOPS limits. `pids_limit` is reconciled with `deploy.resources.limits.pids`; runtime, user namespace, and storage driver options are passed through. Device cgroup rules are passed through as a list. Ulimit scalar values set both soft and hard; mapping syntax requires both values. Device short syntax and long `source`/`target`/`permissions` mappings are handled; remaining platform behavior, numeric ranges, and syntax validation are incomplete. |
| `dns`, `dns_opt`, `dns_search`, `extra_hosts`, `network_mode`, `ipc`, `pid`, `uts`, `cgroup_parent` | `ServiceDefinition` raw fields | Partial | DNS server, option, and search lists plus list/map extra-host forms are mapped to Docker `HostConfig`. Multiple project network attachments, per-network aliases/static addresses, and basic network-mode values are applied. `network_mode`, `ipc`, and `pid` `service:<name>` references select and order the referenced service, then resolve its created container ID for Docker Engine in service and one-off containers. `uts: host` is mapped for service and one-off containers. `external_links` maps existing container names and optional aliases through Docker Engine links; the external container must already be attached to a network shared by the consuming service. The loader rejects services that combine `network_mode` and `networks` or refer to undeclared networks (except implicit `default`). Full Compose normalization and namespace compatibility edge cases remain incomplete. See the official [Docker Compose UTS field reference](https://docs.docker.com/reference/compose-file/services/#uts). |
| CPU, memory, shared memory, and group settings | `ServiceDefinition` raw fields | Partial | `mem_limit`, `memswap_limit`, `mem_reservation`, `mem_swappiness`, `cpu_shares`, `cpuset`, `cpus`, `cpu_quota`, `cpu_period`, `cpu_count`, `cpu_percent`, `oom_kill_disable`, `oom_score_adj`, `shm_size`, and `group_add` are mapped for service and one-off containers. Byte values accept fractional binary units (for example, `1.5gb`) and `deploy.resources.limits.memory`/`cpus`/`pids` plus `reservations.memory` are fallbacks; when both deploy and service-level equivalents are set, mismatched values fail. `deploy.resources.reservations.devices` maps capabilities, driver, count (`all` included), device IDs, and options; service `gpus` maps `all` or a list of GPU requests. `count` and `device_ids` are mutually exclusive. CPU reservations, generic resources, and daemon/platform-specific semantics remain incomplete. |
| `stop_signal` | `ServiceDefinition` raw fields | Partial | The configured signal is applied to service and one-off container creation; every lifecycle path and signal spelling is not verified. |
| `stop_grace_period` | `ServiceDefinition` raw fields | Partial | Fractional and composite duration units are parsed and applied as the Docker Engine container stop timeout. Stop, restart, down, remove with `stop`, and reconciliation/scaling use the service value when no operation timeout is supplied; an explicit stop/restart/down timeout takes precedence. Full duration normalization and platform behavior still need broader compatibility verification. |
| `tty`, `stdin_open`, `init` | `ServiceDefinition` raw fields | Partial | These values are applied when reconciliation creates service containers. `init` is also applied to one-off `run` containers and verified through Docker inspection; the other fields' one-off behavior and full Compose semantics are not verified. |
| `extends`, `include`, `develop`, `x-*` extensions | `ServiceDefinition`, `ComposeProject.extensions` | Partial | Root `x-*` values are retained. `extends` resolves same-file and external service references recursively, merges inherited settings, rebases inherited build/env-file/bind paths to the project file, rejects circular or missing references, and validates the `healthcheck.disable` inheritance constraint. Local `include` paths (string, list, or mapping with `project_directory` and `env_file`) recursively import services and top-level networks, volumes, secrets, and configs; a mapping's path list is merged in order as one included project, with relative build/env/bind/config/secret paths rebased and name conflicts between projects rejected. Remote OCI/Git sources and other parts of the full include schema are not implemented. `develop.watch` executes the five supported actions, supports `initial_sync`, applies rule path plus include/ignore glob filters, and excludes service build-context `.dockerignore` matches, `.git` directories, and Docker Compose editor temporary files. Events for the same service, action, and path are coalesced for a 500 ms quiet period. Matching deletes are removed from the container with `rm -rf`. `!reset` and `!override` are supported for overlay merging. |

### Other service fields in the Compose catalog

The loader may retain these values inside a service's normalized raw mapping even when there is no dedicated Java property. Retention is useful for inspection and configuration rendering, but it does not validate full Compose syntax or apply the value to a container.

| Docker Compose field(s) | Current status | Notes |
| --- | --- | --- |
| `entrypoint`, `command`, `init`, `working_dir`, `user`, `hostname`, `domainname`, `container_name` | Partial | Common command, identity, and process fields are mapped during service and one-off `run` container creation; `init` is passed to Docker Engine for both paths. Scalar/list edge cases and full Compose semantics are not complete. |
| `attach`, `stdin_open`, `tty`, `privileged`, `read_only`, `restart`, `stop_signal`, `stop_grace_period` | Partial | `attach: false` suppresses service log collection during non-detached `up`; explicit `logs` requests still include that service. `stdin_open`, `tty`, `privileged`, `read_only`, `restart`, `stop_signal`, and `stop_grace_period` are mapped for service container creation; other attach behavior remains incomplete. |
| `cap_add`, `cap_drop`, `security_opt`, `devices`, `device_cgroup_rules`, `sysctls`, `group_add`, `ulimits` | Partial | These values are mapped for service and one-off `run` containers; remaining validation and platform-specific semantics remain incomplete. |
| `cpu_count`, `cpu_percent`, `cpu_shares`, `cpu_quota`, `cpu_period`, `cpus`, `cpuset`, `mem_limit`, `mem_reservation`, `mem_swappiness`, `memswap_limit`, `oom_kill_disable`, `oom_score_adj`, `shm_size` | Partial | These listed CPU, memory, OOM, and shared-memory values are mapped to Docker Engine host configuration for service and one-off containers. `deploy.resources.limits.memory`/`cpus` and `reservations.memory` act as fallbacks when service-level values are absent; mismatches are rejected. Daemon/platform behavior and full unit validation are not verified. |
| `dns`, `dns_opt`, `dns_search`, `extra_hosts`, `mac_address`, `network_mode`, `networks`, `pid`, `ipc`, `uts`, `links`, `external_links`, `expose` | Partial | DNS server/options/search lists, `uts: host`, and `expose` are mapped. Multiple project bridge networks can be attached with per-network aliases, static IPv4/IPv6 addresses, and MAC addresses. `service:<name>` references in `network_mode`, `ipc`, and `pid` are supported. `links` entries are validated against project services, select/start linked services first, and add `service:alias` aliases to the linked service on shared project networks. Changing linked aliases recreates the linked service container. `external_links` maps existing container names and aliases using Docker Engine links; the external container must share a network with the consuming service. Links used with non-Compose network modes, top-level network drivers/IPAM, and full short/long syntax normalization remain incomplete. |
| `logging`, `healthcheck`, `deploy`, `configs`, `secrets`, `extends`, `develop`, `volumes_from` | Parsed only or partial | Logging driver/options are applied for service and one-off `run` containers, subject to the driver limitation above. Basic service healthcheck configuration is applied at container creation. File-backed service secrets/configs are applied as read-only bind mounts; see the project resource row above. `extends` is expanded by the loader, while runtime fields inherited from it retain their existing support limits. `volumes_from` accepts project service names and `container:<name>` references with optional `ro`/`rw`; service sources are ordered and resolved to the first existing labeled container. Other fields and secret/config source types remain incomplete. Loader retention must not be interpreted as full runtime support. |
| `annotations`, `pre_start`, `post_start`, `pre_stop`, `provider`, `use_api_socket`, `models`, `pull_policy`, `pull_refresh_after`, `platform`, `scale`, `profiles`, `depends_on` | Parsed only or partial | `pre_start` runs ordered ephemeral containers before a service container's first start, with the service environment, network, and configured volume mounts; hook images, commands, user, privilege, working directory, environment, and `per_replica` are supported. Failed hooks prevent service start and their containers remain for inspection; a later `up` removes those failed hook containers and retries against the still-created service container. Successful hook containers are removed. Later `start`, `restart`, and daemon restart-policy restarts do not repeat successful hooks; changing the hook definition changes the service config hash and recreates the container. `post_start` runs through Docker exec after containers start during `up`, `start`, and `restart`; `pre_stop` runs before a running container is stopped during `stop`, `restart`, `down`, removal with stop enabled, and service recreation. Hook failures fail the enclosing operation. Shell-form hook commands currently use `/bin/sh`; Docker Compose platform-specific shell behavior and one-off `run` lifecycle hooks are not covered; one-off `run` containers execute `post_start` hooks after starting. `profiles`, `depends_on`, `pull_policy` (including time-based refresh windows and the `if_not_present` alias), `platform`, `gpus`, and a subset of `scale` affect the current lifecycle paths. Other newer lifecycle fields need further compatibility work. |

This catalog is a tracking aid, not an exhaustive claim about every Compose Specification version. Consult the official [Compose file reference](https://docs.docker.com/reference/compose-file/) for the current field catalog and report fields absent from this matrix.

## Operation and runtime scope

The Java API declares the operation surface being synchronized from ComposeSharp 3.0.0: `build`, `up`, `down`, `create`, `start`, `stop`, `restart`, `pull`, `push`, `kill`, `run`, `exec`, `attach`, `copy`, `pause`, `ps`, `list`, `top`, `images`, `port`, `logs`, `events`, `scale`, `wait`, `watch`, `export`, `commit`, `viz`, `generate`, `volumes`, and `publish`. These declarations establish scope; declarations are not evidence of implemented behavior.

| Operation group | Current status | Notes |
| --- | --- | --- |
| `start`, `stop`, `restart`, `pause`, `unpause`, `kill`, `remove`, `down` | Partial | Operate on existing containers/resources carrying the selected Compose project label. Existing-service operations load the Compose file to apply active profiles; an explicit service list selects those services, including services outside active profiles. If no Compose file exists and no profiles were requested, selection falls back to project labels, with an explicit service list still filtering by service label. `stop` confirms Docker reports each successfully stopped container as no longer running, polling for up to five seconds; a container that disappears is considered stopped. `remove` with `stop` enabled completes the stop phase for the selected containers before removing them. Batched `stop`, `kill`, `pause`, `unpause`, and `remove` continue after Docker API errors for individual containers; `down` ignores stop errors and treats a concurrently removed container as complete. `down.removeOrphans` removes project containers whose service is absent from the Compose file. `down.removeImages` supports `all` for selected service images and `local` for selected services built without an explicit image name. `down.removeVolumes` removes anonymous volumes attached to removed containers and declared project volumes. `down` removes project networks and declared project volumes only when the selection covers all defined services (or label-only fallback is used). `start` ignores only Docker's 304 already-started response to tolerate a concurrent start, includes dependencies, and waits for dependency readiness; it does not create or reconcile containers. `restart` restarts dependents transitively when their long-form `depends_on` entry sets `restart: true`, in dependency order; `noDeps` skips this expansion, and runtime-policy restarts are unaffected. |
| `ps`, `list` | Partial | `ps` returns project-labeled containers filtered by active profiles, explicit services, and the Docker Compose `status` filter; without a Compose file it falls back to label-only selection when no profiles are requested. Its `status` option and `filter=status=...` accept Docker container states. `quiet` retains only each container ID in the typed `ContainerSummary`; `format` is not applied because this SDK operation returns structured values. Health and exit codes are parsed from Docker status text; mounts and byte sizes come from the Docker list response. Mount type is reported as `volume` when Docker provides a volume name and remains null otherwise. `list` returns typed `Stack` values for discovered projects, with `running`, `exited`, `partial`, or `unknown` status derived from labeled container states; paused/restarting states are `unknown`. Docker's default container listing determines project visibility, so paused/restarting projects may remain listed while stopped-only projects are omitted; `all` includes projects excluded by the default listing. |
| `generate` | Implemented subset | Returns typed `ComposeProjectConfig` with a normalized YAML snapshot and effective interpolation environment (process environment takes precedence over the project `.env`) without daemon access. See [Generate and Watch contract](generate-watch.md). |
| `pull`, `push` | Implemented subset | `pull` honors explicit service `pull_policy`: with no policy it pulls, `missing`/`if_not_present` skip a cached non-`latest` image, `never` and `build` skip, and `always` or a time-based refresh policy pull. `up` and `create` refresh time-policy images after `daily`, `weekly`, `every_<duration>`, or `pull_refresh_after` expires according to Docker Engine `LastTagTime`. Shared image references are pulled once. An explicit operation platform takes precedence over the service `platform`. `pull.ignoreFailures` and `push.ignoreFailures` suppress per-image Docker API and progress-stream failures so remaining images can proceed; unexpected runtime errors and cancellation propagate. Offline contexts reject explicit pull/push/publish, and suppress automatic pulls during `up`, `create`, and `run`. Build requests disable the explicit base-image refresh flag when offline, but Docker may still fetch a missing base image. Pull progress is not emitted, so `quiet` has no additional effect. Other registry semantics still require complete compatibility evidence. |
| `viz`, `volumes` | Implemented subset | `viz` renders a graph from loaded configuration. `volumes` returns typed `VolumesSummary` values for project-labeled Docker volumes; explicit service selection filters the results to volumes mounted by running or stopped project containers of those services. Scope and created-at metadata are unavailable from the configured docker-java response type. |
| `top` | Implemented subset | Uses Docker's process-list endpoint for running selected project containers and returns typed `ContainerProcSummary` values; stopped containers are omitted. A container that exits or is removed between listing and process lookup is skipped, while other Docker errors are propagated. Empty explicit service selection returns an empty list. |
| `images` | Implemented subset | Returns typed `ImageSummary` values for images used by project-labeled containers selected by active profiles or explicit services; without a Compose file and profiles, selection falls back to project labels. `quiet` retains only each image ID in the typed result; `format` is not applied because this SDK operation returns structured values rather than formatted CLI rows. |
| `port` | Implemented subset | Returns typed `PortResult` with the first binding on a running service container. Replica indices are 1-based, and the protocol option accepts Docker Compose's `tcp` and `udp` values; full host-address and output formatting semantics remain to be verified. |
| `logs` | Implemented subset | Streams selected project-labeled containers' stdout/stderr through `ILogConsumer`, with profile or explicit service selection, follow, tail, timestamps, `since`/`until` filters (Unix seconds, ISO-8601 timestamp/date, or relative duration), and optional ANSI stripping. Relative durations are measured from the time the request is made. Without a Compose file and profiles, selection falls back to project labels. Callbacks from multiple containers may run concurrently. Other Compose formatting behavior is not applied. The consumer receives the service name separately, so `noLogPrefix` has no additional effect. |
| `events` | Implemented subset | Streams project-owned container, network, and volume events as typed `ComposeEvent` values with timestamps and actor attributes (null when Docker supplies none). Missing action and ID values are empty strings, matching ComposeSharp. Service filtering honors the context's active profiles; an explicit service list filters to those services, and project-level events are then dropped. The declared `json` formatting option does not alter the typed event stream. |
| `build` | Partial | Builds selected services with local directory contexts, Dockerfiles inside or outside the context, Dockerfile-specific `.dockerignore` precedence and Docker ignore filtering, tags, build args, labels, a single platform (including the service-level fallback), target, cache/pull flags, cache-from, network, memory, shared memory, list- and mapping-form extra hosts, registry auth, and progress callbacks. `progress` accepts `auto`, `tty`, `plain`, `json`, and `quiet`; quiet mode suppresses progress callbacks, while the other formats still receive raw Docker Engine stream/status lines rather than Compose-formatted output. Context archives preserve symbolic links, Unix file modes, and FIFOs; omit Unix sockets; and reject Unix device nodes. Ignore matching covers indented `#` patterns, escaped class members, Unicode scalar wildcards/ranges, and descending ranges. Multiple target platforms are rejected because this Docker Engine build path accepts one platform per request. Remote HTTP(S), Git, and SSH contexts are passed to Docker Engine; remote Dockerfile resolution and credentials are handled by the daemon and are not independently verified. Builder selection, full Docker ignore matching, and several Build Spec fields remain unverified. This is not verified as Docker Compose-conformant. |
| `up`, `create` | Partial | Basic dependency ordering, project-scoped resource setup, config-hash-based reconciliation, replica counts, pull/build selection (including service `pull_policy: build`), and a subset of service fields are applied. `up.noDeps` skips starting and waiting for selected services' dependencies. `up.waitTimeoutSeconds` bounds readiness waits for selected services independently of `dependencyWaitTimeoutSeconds`. `container_name` services reject replica counts above one. `up` waits for supported dependency conditions and optional service readiness; `detach=false` follows selected service and dependency logs through `ILogConsumer`. Healthcheck values are mapped to Docker Engine. `alwaysRecreateDeps` forces selected dependency services to recreate and rejects the incompatible `noRecreate` combination; `forceRecreate` and `noRecreate` are also rejected together. Explicitly configured and image-declared anonymous volumes are reused by replica during recreation unless `renewAnonVolumes` is enabled; full Compose recreate semantics, every runtime field, and complete option behavior remain incomplete. |
| `scale` | Partial | Applies requested replica counts to selected services, keeps the lowest-numbered replicas where possible, and returns typed `ServiceStatus` values. Unless `noDeps` is set, selected services' dependencies are created or started in dependency order at their configured replica counts and readiness conditions are awaited; `noDeps` skips them. Services with `container_name` reject replica counts above one. `timeoutSeconds` is applied when stopping surplus replicas. Full Compose option behavior is not implemented. |
| `wait` | Partial | Returns a `WaitResult` containing per-container exit codes and an aggregate code selected by container ID order. A null or empty service list selects services active under the context profiles; selected running project containers, including one-off containers, are awaited. Docker API wait errors are reported as `-1` for that container. When `downProjectOnContainerExit` is enabled, the first watched container exit tears down all project containers and project networks; named volumes are retained. |
| `export` | Implemented subset | Exports the selected service replica's filesystem as a Docker tar archive to a local path; creates parent directories. Full option and error compatibility remains to be verified. |
| `commit` | Implemented subset | Commits the selected service replica with image reference, author, message, pause behavior, and Dockerfile-style `changes` (`CMD`, `ENTRYPOINT`, `ENV`, `EXPOSE`, `LABEL`, `ONBUILD`, `USER`, `VOLUME`, `WORKDIR` as accepted by Docker Engine; see [Docker Compose commit options](https://docs.docker.com/reference/cli/docker/compose/commit/)). |
| `publish` | Partial | `publishAsync` loads and merges the selected Compose files, includes services from every profile as Docker Compose does, rejects services with bind mounts or a `build` section without an `image` before contacting Docker, pushes the configured image references, then renders the retained model as a normalized `compose.yaml` and pushes an OCI artifact with Docker Compose's project artifact type and Compose file media type. With `resolveImageDigests`, it reads each pushed image manifest digest from its registry and pins the rendered image reference to that digest; already digest-pinned references remain unchanged. Image transfer failures are ignored as Docker Compose does; other runtime failures stop the operation. The artifact digest is returned. Resolved environment values are omitted by default. With `withEnvironment`, referenced service `env_file` files are copied into opaque, path-free OCI layers using Docker Compose's `application/vnd.docker.compose.envfile` media type and layer annotations, and the rendered `env_file` references point to those layers. Custom `ociVersion` and source Compose file layer publication are not implemented; requesting a custom version fails before Docker or registry access. `publishImagesAsync` separately syncs the ComposeSharp 3.0.0 image publishing operation: it tags each selected service image as `repository:service`, pushes it, and returns a per-service outcome for Docker API failures and registry push errors; unexpected runtime errors and cancellation fail the operation. The latter is a sibling SDK extension and is not claimed as Docker Compose behavior. The normalized OCI output inherits loader/model limitations and is not a source-preserving or full `docker compose config` round trip. Registry authentication uses ORAS Java's standard Docker/containers credential configuration for OCI artifact and digest lookups, and project registry credentials for image pushes; insecure transport is opt-in for ORAS operations. |
| `exec` | Implemented subset | Runs a command in the selected running service replica, captures stdout/stderr and exit status, or starts a detached exec. Interactive stdin is read from the process standard input; terminal sizing and signal forwarding are not implemented. |
| `attach` | Implemented subset | Streams selected running container output to process stdout/stderr and optionally forwards process stdin. Detach keys and terminal resize are not implemented. |
| `watch` | Implemented subset | For services with `develop.watch`, recursively watches rule paths, applies include/ignore glob filters, excludes service build-context `.dockerignore` matches, `.git` directories, and Docker Compose editor temporary files, starts/builds selected services unless `noUp`, performs rebuild/restart/sync/sync+restart/sync+exec actions, then emits typed `WatchEvent` values with absolute paths. Events for the same service, action, and path are coalesced for a 500 ms quiet period. Sync rules support `initial_sync` and remove matching deleted files/directories from the container. Services without rules retain the SDK build-context notification stream with the same ignore filtering. When `ComposeWatchOptions.prune` is enabled, rebuilds remove dangling images labeled for the current project after service recreation; tagged images and images from other projects are preserved. See [watch behavior](generate-watch.md). |
| `run` | Partial | Creates a one-off project-labeled container, applies command/entrypoint, environment, labels, mounts, process settings, capabilities, multiple network attachments and per-network aliases/static addresses; service port mappings are unpublished by default and enabled with `ComposeRunOptions.servicePorts`, while extra short-syntax mappings can be supplied with `ComposeRunOptions.publish`. Starts dependencies unless disabled and streams logs unless detached; `ComposeRunOptions.builder().build()` keeps stdin open by default, matching Docker Compose `--interactive=true`, and attached interactive runs forward process stdin. Detached containers are retained. In attached mode, `ComposeRunOptions.builder().build()` retains the container by default and `.remove(true)` removes it after exit, matching Docker Compose's default unless `--rm` is requested. Passing `null` options removes the attached container for backward compatibility. ComposeSharp `3.0.0-32-g648a430` defaults interactive stdin off, so jcompose follows Docker Compose for this option; the Docker Compose behavior remains the compatibility target. Terminal sizing, signal forwarding, lifecycle hooks, and other run options still have incomplete Docker Compose coverage. |
| `copy` | Implemented subset | Copies tar archives between host paths and project service containers, supports 1-based replica selection, fan-out to all replicas, and UID/GID preservation for host-to-container copies. `followLink` follows a top-level host source symlink for host-to-container copies; other symlink and special archive entries are rejected. Hard-link entries are materialized as copies when their in-archive target has already been extracted. The local destination path is checked for symlink ancestors before extraction. Container-to-host extraction uses the requested host path as a directory; `followLink` is not applied in that direction. |

These operations are SDK operations, not full `docker compose` equivalents, and their behavior has not yet been established as Docker Compose-conformant. In particular, do not infer support for every option declared by any operation options record. Cancelling a returned future with `cancel(true)` interrupts its worker and closes owned Docker clients; immediate interruption of an in-flight HTTP request depends on docker-java's configured transport.

Before changing a row to Implemented, add loader and/or engine tests that compare observable behavior with Docker Compose, document the supported subset and limitations, and update this matrix. Use the official [Compose file reference](https://docs.docker.com/reference/compose-file/) as the field catalog.
