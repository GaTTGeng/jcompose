# Docker Compose field support matrix

This matrix tracks **jcompose's** behavior against Docker Compose. ComposeSharp 3.0.0 is the sibling implementation used to synchronize feature scope; it does not define compatibility behavior. A matching Java API type does not mean the field is parsed or applied.

## Status definitions

| Status | Meaning |
| --- | --- |
| Implemented | Parsed and applied by jcompose, with behavior checked against Docker Compose. |
| Partial | A documented subset is parsed or applied; listed gaps remain. |
| Parsed only | Retained in the Java model, with no corresponding runtime behavior yet. |
| Planned | In the ComposeSharp 3.0.0 feature scope, but not implemented or verified in jcompose. |
| Unsupported | Known unsupported behavior; no compatibility claim is made. |

The repository is currently an early `3.0.0-SNAPSHOT`. When no Compose filename is explicitly supplied, jcompose prefers `compose.yaml` and searches conventional filenames from the working directory upward. Project loading also merges the matching optional conventional override file. Most Compose-shaped service fields are retained in `ServiceDefinition` as raw values. The engine implements a limited subset of build and service lifecycle behavior. Therefore, **no field should be read as full Docker Compose support unless its row explicitly says Implemented**. At this snapshot, no Compose service field has been verified as fully implemented against Docker Compose.

## Project and service fields

| Docker Compose field or behavior | jcompose model/API | Current status | Notes and target behavior |
| --- | --- | --- | --- |
| `services` and service names | `ComposeProject.services`, `ServiceDefinition` | Partial | The loader requires a non-empty service mapping and retains each service mapping. It currently rejects a service without `image` or `build`. |
| `image`, `build`, `container_name`, `command`, `entrypoint` | `ServiceDefinition` raw fields | Partial | `build` invokes Docker Engine for local contexts and applies a subset of build options. Remote contexts are unsupported. Local Dockerfiles outside the context are staged into the archive; `.dockerignore` is applied by the context archiver, but full Docker CLI matching compatibility is not verified. Basic container creation/reconciliation applies a subset of service settings. |
| `environment`, `env_file` | `ServiceDefinition` raw fields | Partial | Interpolation and basic env-file loading exist; simple environment maps/lists are applied at container creation. Key-only `environment` entries pass through matching host values and are omitted when unresolved; bare keys in normal `env_file` format become empty values. `env_file.required: false` skips a missing optional file, and `format: raw` preserves values without dotenv parsing. All Compose precedence/quoting rules are not implemented. See [loader compatibility](loader-compatibility.md). |
| `ports`, `expose` | `ServiceDefinition` raw fields | Partial | Basic short and long port mappings are applied. Ranges, all protocol/address combinations, and Compose formatting need conformance coverage. |
| `volumes` | `ServiceDefinition` raw fields | Partial | Basic short/long bind and named mounts are applied. Anonymous, Windows path edge cases, mount options, and external-volume semantics are not verified. |
| `depends_on`, `profiles` | `ServiceDefinition`, `ComposeProjectContext` | Partial | Profile selection and stable dependency ordering exist for create/up/start. `up` and `start` wait for `service_started`, `service_healthy`, and `service_completed_successfully` dependencies; full profile activation and all dependency edge cases remain incomplete. |
| `healthcheck`, `restart`, `deploy.replicas`, `deploy.restart_policy` | `ServiceDefinition` raw fields | Partial | Basic healthcheck test/timing values, service restart policy, and replica counts are mapped. Healthcheck durations accept fractional and composite units (`1.5s`, `1m30s`). `deploy.restart_policy` takes precedence over `restart` and maps `none`, `any`, and `on-failure` plus `max_attempts` to Docker Engine; `delay` and `window` are not represented by the container restart policy. Other duration normalization and deployment semantics remain incomplete. |
| `networks`, `volumes`, `secrets`, `configs` at project scope | `ComposeProject` resource names and definitions | Partial | Network, volume, secret, and config definitions are retained and rendered. Project resources apply custom names, external-resource lookup, network driver/options, attachable/internal/IPv6 flags, subnet/IP-range/gateway IPAM entries, and volume drivers/options. File-backed secrets/configs granted to services are mounted read-only for service containers and one-off `run`; default targets are `/run/secrets/<name>` for secrets and `/<name>` for configs, and explicit targets are supported. The Docker daemon must be able to read the resolved host path, and host file permissions are unchanged. External, environment-backed, and inline-content secrets/configs are unsupported; file-source `uid`/`gid`/`mode` values are retained but not applied by this bind-mount backend. Windows secrets require an explicit target. External networks/volumes must already exist; IPAM options and several resource fields remain unapplied. |
| `labels`, `logging`, `hostname`, `domainname`, `user`, `working_dir` | `ServiceDefinition` raw fields | Partial | Service labels and several container identity/process fields are applied. Logging driver/options are passed to Docker Engine for service and one-off `run` containers; driver names must be present in docker-java 3.7.1's enum, so custom plugin driver names outside that list fail clearly. The remaining Docker Compose semantics are incomplete. |
| `privileged`, `read_only`, `tmpfs`, `cap_add`, `cap_drop`, `security_opt`, `devices`, `device_cgroup_rules`, `blkio_config`, `sysctls`, `ulimits`, `pids_limit`, `runtime`, `userns_mode`, `storage_opt` | `ServiceDefinition` raw fields | Partial | These values are mapped into Docker `HostConfig` for service and one-off `run` containers. `blkio_config` supports weight, per-device weights, read/write bytes-per-second, and read/write IOPS limits. `pids_limit` is reconciled with `deploy.resources.limits.pids`; runtime, user namespace, and storage driver options are passed through. Device cgroup rules are passed through as a list. Ulimit scalar values set both soft and hard; mapping syntax requires both values. Device short syntax and long `source`/`target`/`permissions` mappings are handled; remaining platform behavior, numeric ranges, and syntax validation are incomplete. |
| `dns`, `dns_opt`, `dns_search`, `extra_hosts`, `network_mode`, `ipc`, `pid`, `cgroup_parent` | `ServiceDefinition` raw fields | Partial | DNS server, option, and search lists plus list/map extra-host forms are mapped to Docker `HostConfig`. Multiple project network attachments, per-network aliases/static addresses, and basic network-mode values are applied. Service references and full Compose normalization are not implemented. |
| CPU, memory, shared memory, and group settings | `ServiceDefinition` raw fields | Partial | `mem_limit`, `memswap_limit`, `mem_reservation`, `mem_swappiness`, `cpu_shares`, `cpuset`, `cpus`, `cpu_quota`, `cpu_period`, `cpu_count`, `cpu_percent`, `oom_kill_disable`, `oom_score_adj`, `shm_size`, and `group_add` are mapped for service and one-off containers. Byte values accept fractional binary units (for example, `1.5gb`) and `deploy.resources.limits.memory`/`cpus`/`pids` plus `reservations.memory` are fallbacks; when both deploy and service-level equivalents are set, mismatched values fail. `deploy.resources.reservations.devices` maps capabilities, driver, count (`all` included), device IDs, and options; service `gpus` maps `all` or a list of GPU requests. `count` and `device_ids` are mutually exclusive. CPU reservations, generic resources, and daemon/platform-specific semantics remain incomplete. |
| `stop_signal` | `ServiceDefinition` raw fields | Partial | The configured signal is applied to service and one-off container creation; every lifecycle path and signal spelling is not verified. |
| `stop_grace_period` | `ServiceDefinition` raw fields | Partial | Fractional and composite duration units are parsed and applied as the Docker Engine container stop timeout and on reconciliation/scaling stop calls; all stop paths and normalization are not verified. |
| `tty`, `stdin_open`, `init` | `ServiceDefinition` raw fields | Partial | These values are applied when reconciliation creates service containers; other container creation paths and full Compose behavior are not verified. |
| `extends`, `include`, `develop`, `x-*` extensions | `ServiceDefinition`, `ComposeProject.extensions` | Partial | Root `x-*` values are retained. `!reset` and `!override` overlay tags are recognized by multi-file loading; Compose-level expansion/merge semantics for other constructs are not implemented. |

### Other service fields in the Compose catalog

The loader may retain these values inside a service's normalized raw mapping even when there is no dedicated Java property. Retention is useful for inspection and configuration rendering, but it does not validate full Compose syntax or apply the value to a container.

| Docker Compose field(s) | Current status | Notes |
| --- | --- | --- |
| `entrypoint`, `command`, `init`, `working_dir`, `user`, `hostname`, `domainname`, `container_name` | Partial | Common command, identity, and process fields are mapped during basic container creation; scalar/list edge cases and full Compose semantics are not complete. |
| `attach`, `stdin_open`, `tty`, `privileged`, `read_only`, `restart`, `stop_signal`, `stop_grace_period` | Partial | `stdin_open`, `tty`, `privileged`, `read_only`, `restart`, `stop_signal`, and `stop_grace_period` are mapped for service container creation; attach behavior remains incomplete. |
| `cap_add`, `cap_drop`, `security_opt`, `devices`, `device_cgroup_rules`, `sysctls`, `group_add`, `ulimits` | Partial | These values are mapped for service and one-off `run` containers; remaining validation and platform-specific semantics remain incomplete. |
| `cpu_count`, `cpu_percent`, `cpu_shares`, `cpu_quota`, `cpu_period`, `cpus`, `cpuset`, `mem_limit`, `mem_reservation`, `mem_swappiness`, `memswap_limit`, `oom_kill_disable`, `oom_score_adj`, `shm_size` | Partial | These listed CPU, memory, OOM, and shared-memory values are mapped to Docker Engine host configuration for service and one-off containers. `deploy.resources.limits.memory`/`cpus` and `reservations.memory` act as fallbacks when service-level values are absent; mismatches are rejected. Daemon/platform behavior and full unit validation are not verified. |
| `dns`, `dns_opt`, `dns_search`, `extra_hosts`, `mac_address`, `network_mode`, `networks`, `pid`, `ipc`, `uts`, `links`, `external_links`, `expose` | Partial | DNS server/options/search lists, `uts`, and `expose` are mapped. Multiple project bridge networks can be attached with per-network aliases, static IPv4/IPv6 addresses, and MAC addresses. Other fields, service references, top-level network drivers/IPAM, and full short/long syntax normalization are not implemented. |
| `logging`, `healthcheck`, `deploy`, `configs`, `secrets`, `extends`, `develop`, `volumes_from` | Parsed only or partial | Logging driver/options are applied for service and one-off `run` containers, subject to the driver limitation above. Basic service healthcheck configuration is applied at container creation. File-backed service secrets/configs are applied as read-only bind mounts; see the project resource row above. `volumes_from` accepts project service names and `container:<name>` references with optional `ro`/`rw`; service sources are ordered and resolved to the first existing labeled container. Other fields and secret/config source types remain incomplete. Loader retention must not be interpreted as full runtime support. |
| `annotations`, `post_start`, `pre_stop`, `provider`, `use_api_socket`, `models`, `pull_policy`, `platform`, `scale`, `profiles`, `depends_on` | Parsed only or partial | `profiles`, `depends_on`, `pull_policy` (including the `if_not_present` alias and always-pull behavior for `latest`), `platform`, `gpus`, and a subset of `scale` affect the current lifecycle paths. Time-based pull policies and newer lifecycle fields need explicit runtime support and compatibility work. |

This catalog is a tracking aid, not an exhaustive claim about every Compose Specification version. Consult the official [Compose file reference](https://docs.docker.com/reference/compose-file/) for the current field catalog and report fields absent from this matrix.

## Operation and runtime scope

The Java API declares the operation surface being synchronized from ComposeSharp 3.0.0: `build`, `up`, `down`, `create`, `start`, `stop`, `restart`, `pull`, `push`, `kill`, `run`, `exec`, `attach`, `copy`, `pause`, `ps`, `list`, `top`, `images`, `port`, `logs`, `events`, `scale`, `wait`, `watch`, `export`, `commit`, `viz`, `generate`, `volumes`, and `publish`. These declarations establish scope; declarations are not evidence of implemented behavior.

| Operation group | Current status | Notes |
| --- | --- | --- |
| `start`, `stop`, `restart`, `pause`, `unpause`, `kill`, `remove`, `down` | Partial | Operate on existing containers/resources carrying the selected Compose project label. Existing-service operations load the Compose file to apply active profiles; an explicit service list selects those services, including services outside active profiles. If no Compose file exists and no profiles were requested, selection falls back to project labels, with an explicit service list still filtering by service label. `stop` confirms Docker reports each successfully stopped container as no longer running, polling for up to five seconds; a container that disappears is considered stopped. `remove` with `stop` enabled completes the stop phase for the selected containers before removing them. Batched `stop`, `kill`, `pause`, `unpause`, and `remove` continue after Docker API errors for individual containers; `down` ignores stop errors and treats a concurrently removed container as complete. `down` removes project networks and requested volumes only when the selection covers all defined services (or label-only fallback is used). `start` also includes dependencies and waits for dependency readiness; it does not create or reconcile containers. |
| `ps`, `list` | Partial | `ps` returns project-labeled containers filtered by the active profiles or explicit services; without a Compose file it falls back to label-only selection when no profiles are requested. `list` returns typed `Stack` values for discovered projects. Health, mounts, container exit codes, and all output options do not yet match the complete ComposeSharp 3.0.0 contracts. |
| `generate` | Implemented subset | Returns typed `ComposeProjectConfig` with a normalized YAML snapshot from retained loader configuration without daemon access. Environment output remains empty because the loaded model does not retain the interpolation environment. See [Generate and Watch contract](generate-watch.md). |
| `pull`, `push` | Implemented subset | `pull` honors explicit service `pull_policy`: with no policy it pulls, `missing`/`if_not_present` skip a cached non-`latest` image, `never` and `build` skip, and `always` or a time-based refresh policy pull. Shared image references are pulled once. An explicit operation platform takes precedence over the service `platform`. Offline contexts reject explicit pull/push/publish, and suppress automatic pulls during `up`, `create`, and `run`. Build requests disable the explicit base-image refresh flag when offline, but Docker may still fetch a missing base image. Pull progress is not emitted, so `quiet` has no additional effect. Registry and failure-option semantics still require complete compatibility evidence. |
| `viz`, `volumes` | Implemented subset | `viz` renders a graph from loaded configuration. `volumes` returns typed `VolumesSummary` values for project-labeled Docker volumes; scope and created-at metadata are unavailable from the configured docker-java response type, and service filtering is currently ignored. |
| `top` | Implemented subset | Uses Docker's process-list endpoint for running selected project containers and returns typed `ContainerProcSummary` values; stopped containers are omitted. Empty explicit service selection returns an empty list. |
| `images` | Implemented subset | Returns typed `ImageSummary` values for images used by project-labeled containers selected by active profiles or explicit services; without a Compose file and profiles, selection falls back to project labels. The current implementation does not apply `quiet` or `format`. |
| `port` | Implemented subset | Returns typed `PortResult` with the first binding on a running service container. Replica indices are 1-based; full Docker Compose host-address and output formatting semantics remain to be verified. |
| `logs` | Implemented subset | Streams selected project-labeled containers' stdout/stderr through `ILogConsumer`, with profile or explicit service selection, follow, tail, timestamps, and optional ANSI stripping. Without a Compose file and profiles, selection falls back to project labels. Callbacks from multiple containers may run concurrently. `since`, `until`, and other Compose formatting behavior are not applied. The consumer receives the service name separately, so `noLogPrefix` has no additional effect. |
| `events` | Implemented subset | Streams project-owned container, network, and volume events as typed `ComposeEvent` values with timestamps and actor attributes. Service filtering honors the context's active profiles; an explicit service list filters to those services, and project-level events are then dropped. The declared `json` formatting option does not alter the typed event stream. |
| `build` | Partial | Builds selected services with local directory contexts, Dockerfiles inside or outside the context, Dockerfile-specific `.dockerignore` precedence and Docker ignore filtering, tags, build args, labels, a single platform (including the service-level fallback), target, cache/pull flags, cache-from, network, memory, shared memory, extra hosts, registry auth, and progress callbacks. Multiple target platforms are rejected because this Docker Engine build path accepts one platform per request. Remote contexts, builder selection, full Docker ignore matching, and several Build Spec fields are not verified. This is not verified as Docker Compose-conformant. |
| `up`, `create` | Partial | Basic dependency ordering, project-scoped resource setup, config-hash-based reconciliation, replica counts, pull/build selection (including service `pull_policy: build`), and a subset of service fields are applied. `up` waits for supported dependency conditions and optional service readiness; healthcheck values are mapped to Docker Engine. Anonymous-volume behavior, full Compose recreate semantics, every runtime field, and complete option behavior remain incomplete. |
| `scale` | Partial | Applies requested replica counts to selected services, keeps the lowest-numbered replicas where possible, and returns typed `ServiceStatus` values. `timeoutSeconds` is applied when stopping surplus replicas. Dependency scaling and full Compose option behavior are not implemented. |
| `wait` | Partial | Returns a `WaitResult` containing per-container exit codes and an aggregate code selected by container ID order. A null or empty service list selects services active under the context profiles; selected running project containers, including one-off containers, are awaited. Docker API wait errors are reported as `-1` for that container. `downProjectOnContainerExit` is not applied. |
| `export` | Implemented subset | Exports the selected service replica's filesystem as a Docker tar archive to a local path; creates parent directories. Full option and error compatibility remains to be verified. |
| `commit` | Implemented subset | Commits the selected service replica with image reference, author, message, and pause behavior. Dockerfile-style `changes` are rejected because the configured docker-java commit API does not expose that Docker Engine parameter. |
| `publish` | Implemented subset | Returns typed `PublishResult` values, tags each selected service image as `repository:service`, and pushes it with project registry credentials. Digest resolution, environment packaging, OCI version selection, and insecure registries are rejected as unsupported. |
| `exec` | Implemented subset | Runs a command in the selected running service replica, captures stdout/stderr and exit status, or starts a detached exec. Interactive stdin is read from the process standard input; terminal sizing and signal forwarding are not implemented. |
| `attach` | Implemented subset | Streams selected running container output to process stdout/stderr and optionally forwards process stdin. Detach keys and terminal resize are not implemented. |
| `watch` | Implemented subset | Watches local build contexts recursively and emits typed `WatchEvent` values with absolute changed paths as `rebuild` events without starting services. This is a filesystem notification stream, not the `develop.watch` rebuild/sync/restart workflow. Notifications may repeat; `prune` is unsupported. |
| `run` | Implemented subset | Creates a one-off project-labeled container, applies command/entrypoint, environment, labels, mounts, process settings, capabilities, multiple network attachments and per-network aliases/static addresses, and ports; starts dependencies unless disabled and streams logs unless detached. Interactive stdin forwarding, full Compose run semantics, and every service field are not implemented. The default removal behavior follows the source API contract: omitted options remove after attached completion; explicit options control `remove`. |
| `copy` | Implemented subset | Copies tar archives between host paths and project service containers, supports 1-based replica selection, fan-out to all replicas, and UID/GID preservation for host-to-container copies. Symlinks and non-file/directory archive entries are rejected; `followLink` is not applied. Container-to-host extraction uses the requested host path as a directory. |

These operations are SDK operations, not full `docker compose` equivalents, and their behavior has not yet been established as Docker Compose-conformant. In particular, do not infer support for every option declared by any operation options record. Cancelling a returned future with `cancel(true)` interrupts its worker and closes owned Docker clients; immediate interruption of an in-flight HTTP request depends on docker-java's configured transport.

Before changing a row to Implemented, add loader and/or engine tests that compare observable behavior with Docker Compose, document the supported subset and limitations, and update this matrix. Use the official [Compose file reference](https://docs.docker.com/reference/compose-file/) as the field catalog.
